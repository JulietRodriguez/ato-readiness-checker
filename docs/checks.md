# Readiness checks

Generated by `ato-readiness-checker list-checks --markdown`. CI fails if this file is out of date.

Severity is how much a failed check matters for the package (the tool's own scale). Some checks raise or lower the severity of individual issues; the check description says when.

| ID | Check | Category | Severity | What it looks for |
|---|---|---|---|---|
| PKG-001 | Package has an SSP, Assessment Results and a POA&M | package | critical | An authorization package needs all three core documents for the AO to weigh risk. |
| SSP-001 | Required SSP sections are present | ssp | high | System characteristics, categorization, boundary, architecture, data flow, components, inventory, users and control implementation must all be filled in. |
| SSP-002 | Security categorization is consistent (FIPS 199 high-water mark) | ssp | high | Each C/I/A impact must be at least the highest impact of the system's information types, and the overall sensitivity level must equal the highest of C, I and A. |
| SSP-003 | Key roles are assigned to people | ssp | medium | System Owner, Authorizing Official and ISSO each need a named party in metadata responsible-parties. |
| SSP-004 | No draft or placeholder language | ssp | medium | Text such as TBD, TODO, '[insert ...]' or 'review and refine' means the SSP is still a draft. |
| CTRL-001 | Every baseline control has an implementation statement | controls | high | Each control in the selected baseline must appear in the SSP's implemented-requirements. |
| CTRL-002 | Implemented requirements describe how the control is met | controls | high | Each implemented-requirement needs narrative text (by-components description, statement narrative or remarks) explaining the implementation. Not-applicable controls are covered by CTRL-006 instead. |
| CTRL-003 | Implementation status is present, valid and consistent | controls | medium | Each control needs an implementation status (implemented, partial, planned, alternative, not-applicable), and the control-level and component-level statuses must agree. |
| CTRL-004 | SSP status agrees with the assessment | controls | medium | A control the SSP calls 'implemented' should not have a not-satisfied finding, and a control assessed as satisfied should not still be 'planned' in the SSP. |
| CTRL-005 | Planned and partial controls are tracked on the POA&M | controls | medium | A control the SSP says is only planned or partially implemented is a known gap, so it should have a POA&M item. |
| CTRL-006 | Not-applicable controls are justified | controls | low | A control marked not-applicable needs text explaining why. |
| AR-001 | Assessment Results contain results and findings | assessment | critical | Each Assessment Results document needs at least one result with findings. |
| AR-002 | Every in-scope control was assessed | assessment | medium | Each baseline control (or each SSP control when no baseline is given) should have a finding or be listed in the assessment's reviewed controls. |
| AR-003 | Assessment is current | assessment | medium | The most recent assessment result should fall within the allowed age (default 365 days). |
| TRC-001 | Every not-satisfied finding has a POA&M item | traceability | high | Each weakness the assessment found must be tracked on the POA&M (or the AO must be told why not). |
| TRC-002 | Every POA&M item traces to an assessment finding | traceability | medium | Each open POA&M item should link (by UUID or control) to a not-satisfied finding in the Assessment Results, so the AO can see where the weakness came from. |
| POAM-001 | POA&M items have a scheduled completion date | poam | high | Every item that is not closed needs a due date (risk deadline or scheduled-completion-date). |
| POAM-002 | Open POA&M items have dated milestones | poam | medium | Each open item needs at least one milestone, and each milestone needs a date. |
| POAM-003 | POA&M items have a point of contact | poam | medium | Someone must own each item: a point-of-contact prop, an origin party, or a task responsible party. |
| POAM-004 | No overdue POA&M items | poam | high | An open item past its due date needs a new date with a documented reason, or closure. This is a package problem (the POA&M is not being maintained). Overdue Critical/High items are raised to critical. |
| POAM-005 | POA&M items record a severity | poam | low | Without a severity (Critical/High/Moderate/Low or CAT I/II/III) the item can't be prioritized. |
| POAM-006 | Milestones fall on or before the item's due date | poam | low | A milestone scheduled after the completion date means the plan and the due date disagree. |
| REF-001 | All UUID references resolve | references | high | Every finding-uuid, risk-uuid, observation-uuid, component-uuid, party-uuid and '#uuid' link must point at an object in the same document or another document in the package. |
| REF-002 | Assessed subjects are described in the SSP | references | low | Observation subjects (components, inventory items) in the Assessment Results should match objects in the SSP. A miss can mean the assessment covered something outside the documented boundary, or that the two tools use different IDs. |
| REF-003 | POA&M identifies the same system as the SSP | references | medium | The POA&M system-id should match one of the SSP's system-ids. |
| REF-004 | UUIDs are unique within each document | references | medium | OSCAL requires each object's UUID to be unique in its document; duplicates make references ambiguous. |
| REF-005 | OSCAL versions are declared and consistent | references | low | Each document should declare metadata/oscal-version, and the package should use one OSCAL version. |
| REF-006 | Documents are valid against the NIST OSCAL schemas | references | high | Each document must validate against NIST's OSCAL JSON Schema for its model, or tools that import the package (eMASS, FedRAMP automation, GRC platforms) may reject it. |
| RISK-001 | Open Critical, High or CAT I weaknesses | risk | high | Lists each open Critical, High or CAT I item for the AO. This is risk, not a package defect, so it does not affect the readiness score or level; open Critical items are critical issues and High/CAT I items are high issues for the --fail-on gate. |
| RISK-002 | Accepted risks are listed for the AO | risk | info | Items with an approved deviation (risk acceptance) are listed so the AO sees every risk that is being carried rather than fixed. Informational; does not affect the score or level. |
